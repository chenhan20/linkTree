## 一句話任務

只以 `strava.html` 作為功能、資料與互動的唯一程式基準，從零建立 `TAIWAN RIDE CINEMA／台灣騎行電影` 新版本；完全不得開啟、閱讀、沿用或比較任何既有 Fable 版本。

## 這次真正要改變的地方

`strava.html` 的資料功能必須完整保留，但以下介面問題必須徹底改變：

1. 首屏不能再由 `1,926 KM` 霸佔主要視覺。
2. 不再讓每個 view 都是同一套「標題＋線框區塊＋長頁往下讀」。
3. Canvas 不只是背景裝飾，必須與 GPS、海拔、訓練狀態或資料事件連動。
4. 寫實人物不能再退回向量、SVG、火柴人或 3D 玩具。
5. 9 個既有模組不能被不清楚的新名稱藏起來。
6. 關閉動畫後，首頁資訊層級與各 view 的使用方式仍要和原版明顯不同。

## 創作自由：每一頁都要大改，但由資料決定答案

這份計畫只固定產品目標、功能邊界、資料誠實與驗收標準，不替每個 view 指定唯一版型。Fable 可以自由決定每頁的構圖、視覺隱喻、攝影場景、Canvas／Three.js 技法、動畫節奏和互動方式，只要創意是從該頁的真實資料與用途推導出來。

每個 view 開工時只做一次很短的局部判讀：

1. 這頁最重要的資料形狀是時間、地理、比較、因果、身體訊號，還是訓練決策？
2. 使用者進來最想回答的第一個問題是什麼？
3. 哪一個既有互動絕對不能丟？
4. 什麼場景、動畫或空間關係能讓資料更容易理解？

判讀後直接實作，不需要先寫長篇提案或等待確認。

九個 view 都必須有自己的 signature concept，不能共用同一套大卡、長列表、進場動畫或背景模板。允許大幅重新排列資訊、改變首屏、建立新 Canvas 視覺化、增加局部探索與轉場；也允許不採用本文件後面提供的版型靈感，只要結果更適合真實資料。

Fable 不得為了自由發揮而生成假資料、改變資料口徑、隱藏原功能，或用與資料無關的動畫填滿畫面。創意強度可以很高，資料可信度必須保持不變。

### 真正要學的是合成方式，不是照抄畫面

Anthropic 首屏不是把寫實主體全部用 Canvas primitive 畫出來。它以照片級／動態點陣影像建立真實場景，再讓全尺寸 Canvas 疊加轉場、柔化、粒子、軌跡與互動，因此能同時保有真實感與程式動態。

本專案採用相同的分層思路：

1. 寫實底層：桌機與 iPhone 使用已提供的照片級爬坡影片；HTML video 保持獨立，Canvas 只在其上方疊加資料與環境動態，不重新畫車手。
2. 空間層：前景遮擋、失焦植物、霧、光暈、雨、水氣與不同速度的視差，製造鏡頭深度。
3. Canvas 層：GPS 光軌、海拔線、資料粒子、局部扭曲、擦拭轉場、殘影與狀態反應。
4. UI 層：文字、按鈕、圖表和操作維持清楚，不畫進 Canvas，避免模糊與無法操作。

特別要求：

- 不得使用 Canvas、SVG 或 CSS primitive 直接畫真人車手。
- 不得把靜態大圖加一點粒子就稱為 Anthropic 等級的 Canvas。
- 至少要有前景、中景、主體、遠景與資料動態五個可獨立運動的層次。
- 動態必須慢、連續、有景深，不做廉價霓虹掃描、滿屏抖動或遊戲 HUD。
- 場景切換要像鏡頭與天氣在變化，不是整頁 fade-in／fade-out。
- Canvas 動態要受 `strava.html` 的 GPS、海拔、訓練狀態或真實資料事件控制。
- 可以借鑑技術精神，但不得複製 Anthropic 的品牌、文字、素材、程式碼、顏色或版面。

## 9 個 view 的創作任務

以下內容描述每頁應回答的問題與可能方向，不是指定稿。Fable 可以提出並直接實作更好的資料驅動解法；不要九頁照著同一模板套用。

### 現況 Overview

- 核心問題：今天的狀態、下一步與最值得注意的變化是什麼？
- 可以採用 TODAY 決策首頁、陽明山清晨或台北盆地環境，但具體舞台由資料決定。
- 狀態、下一堂、上一堂與警告應先於 Season snapshot；呈現方式可自由設計。

### 計畫 Plan

- 核心問題：目前位於訓練週期的哪裡，下一步和驗收點是什麼？
- 可以使用訓練旅程、道路、軌道、日曆或其他更適合課表資料的形式，不再先呈現 21 堂長列表。
- 目前週、下一堂、前後測與完成狀態必須一眼可見。
- 點擊節點仍使用既有詳情內容。
- 背景是向前延伸的台灣山路或河濱道路。

### 活動紀錄 Log

- 核心問題：最近做了什麼，哪一趟值得打開，以及活動之間形成什麼節奏？
- 可以採用活動時間軸、電影膠卷、路線記憶或其他從日期與活動類型長出的形式。
- 每天先顯示一個摘要，展開後保留活動詳情、報告、Strava、課表、分段與 3D 按鈕。
- 背景使用河濱夜景或雨後城市道路，對比必須壓低。

### ITT

- 核心問題：這條路線目前表現如何，在哪裡失去時間，下一次怎麼突破？
- 建議一次讓一條路線成為主舞台，但可自由設計路線選擇與資料探索方式；不要讓 12 條路線全部用相同大卡連續往下堆。
- 其他路線以挑戰選擇器、縮圖或索引切換。
- 保留全部 35 段、PR、KOM 差距、嘗試次數、狀態與 3D replay。
- 背景由該路線的真實 GPS 與海拔生成台灣山路地形。

### 攻略 Playbook

- 核心問題：在目前條件下該採取哪個策略，為什麼？
- 保留全部指南內容，可以使用條件式查詢、決策路徑、情境卡或其他適合規則資料的方式。
- 先選情境，例如疲勞、下雨、沒功率計、DOMS 高，再展開既有建議。
- 不新增訓練執行模式。
- 背景使用隧道出口、道路分岔或雨霧山路。

### 地圖 Atlas

- 核心問題：我在哪些地方騎過、哪些路線最熟，以及下一個值得探索的區域在哪裡？
- 保留目前所有 GPS、縮放、拖曳、行政區、路段 chips、暈染和標籤功能。
- 可以是立體台灣騎行地景、路網記憶場或其他地理資料驅動形式，但真實軌跡與行政區資料仍是核心。
- 路線流光、海拔、霧與城市光可以動，地圖文字保持清楚。

### 趨勢 Trends

- 核心問題：什麼正在變強、變弱或改變形狀，證據是什麼？
- 可以採用比較工作台、時間鏡頭或其他跨期間分析方式，不要把全部圖表一張張往下排列。
- 保留月量、年度互追、訓練時段、功率曲線、Power Shift、六圍和生涯總量。
- 使用明確的圖表選擇器與共用時間範圍；一次突出一個分析問題。
- 背景使用台北盆地夜景或抽象低對比城市光場。

### 收成 Harvest

- 核心問題：投入經過多久後轉化成什麼成果，現在距離損益線多遠？
- 保留目前投入、延遲與收成資料。
- 可以使用因果時間線、季節生長、延遲波或其他能追蹤投入與結果的資料形式。
- 背景使用稻田晨光、茶園或季節性植物，但不可變成農業網站。

### 身體 Body

- 核心問題：今天和個人基準相比改變了什麼，哪些訊號可信，哪些只是資料空窗？
- 第一屏應先回答變化與判讀；具體視覺化由 HRV、睡眠、DOMS、負荷與缺值形狀決定。
- 保留 DOMS、HRV、靜息心率、睡眠、eFTP、負荷爬升、效率、Pw:HR 與左右平衡。
- 再由指標選擇器進入完整圖表。
- 背景使用森林霧氣、呼吸般的光影與非常低調的生物訊號。

## 導覽原則

- 9 個原始頁面視為 9 個功能模組，不要求永遠維持 9 個同等重量的頂層頁面，可以重新組合成新的產品入口。
- 建議的新入口為 TODAY／TRAIN／RIDE／REVIEW／ALL，但 Fable 可以根據資料提出更好的少量分組。
- TODAY 可以組合 Overview、Body 摘要、下一堂 Plan 與警告。
- TRAIN 可以組合 Plan 與 Playbook。
- RIDE 可以組合 Log、ITT 與 Atlas。
- REVIEW 可以組合 Trends、Harvest 與 Body 完整分析。
- ALL 提供 9 個原始模組的直接入口。
- 重組只發生在新 app shell 與導覽層；不要先把 9 個模組的資料計算和核心 render 攪成一個巨大函式。
- 原名稱、hash 與直接入口先全部保留為相容路徑。新 hub 穩定後可以在畫面上降低舊入口權重，但不可讓深連結失效。
- 同一模組可以在不同 hub 顯示不同深度，例如 Body 摘要出現在 TODAY，完整 Body 分析留在 REVIEW；共用同一資料來源，不複製計算。
- 如果某個 hub 重組失敗，只回退該 hub，不影響其他已完成模組。
- 桌面返回、手機返回、drawer 關閉與 modal 關閉都要清楚。
- 手機可使用底部用途導覽，再由清楚的模組選單進入 9 個 view。
- 任一既有功能最多兩次點擊可到達。

## 背景與可讀性規則

- 每個 view 只允許一個主要寫實場景，不堆多張照片。
- 文字下方必須有穩定的暗色閱讀場，不可讓高對比山脈、光軌或城市燈穿過文字。
- 主要視覺活動集中在留白區、右側或下緣。
- 背景不承擔唯一資訊；關閉背景後資料仍完整。
- OVERDRIVE：完整景深、霧、雨、視差、GPS 流光。
- ACTIVE：降低粒子和更新頻率，保留資料事件。
- QUIET／reduced motion：保留依狀態生成的靜態終態。
- 手機裁切場景並降低粒子，不得換回向量背景或向量人物。

## 整夜自主作業協定

這是一個可持續一整晚的長任務。請自行拆成可獨立完成、可驗證、可中斷的 tasks，不要把全部工作塞進一次巨大修改，也不要在前一小時把時間與使用額度燒在完整重讀、長篇分析或大量視覺變體。

只要本計畫尚未完成，就持續自主往下一個 task 作業，不設定截止時間，也不需要每完成一小步就等待使用者回覆。若 Claude 因使用額度或系統限制被暫停，先保留目前可執行版本並把精確斷點寫進 `docs/strava-cinema-overnight-progress.md`，接著等待限制釋放；恢復後直接從斷點繼續，不重新分析、不重做已完成 task。唯一正常停點是 Task 6 完成後的使用者方向確認閘門，未取得確認不得提前執行 Task 7 完整測試。

### 使用額度與時間原則

- 把完成度放在持續推進，而不是一次輸出最大量。
- Task 0 可以完整讀取一次 `strava.html` 以掌握所有功能；之後每個 task 只讀該模組的必要區段，禁止掃描完整 repository 或重讀整份來源。
- 不重做已經通過的功能，不反覆產生相同報告，不為每個小改動截十張圖。
- 每個 hub 第一輪只選一個清楚的 signature concept，不同時生成多個昂貴變體。
- 先完成結構、資料與互動，再做該 task 的視覺精修；不可整晚只做 Hero 或背景素材。
- 可以使用高推理處理架構和疑難 bug，但機械搬移、樣式調整與重複測試應保持精簡。
- 不要為了看起來在工作而空轉、等待或重複測試；完成一個可預覽結果後立即進下一個 task。
- 使用者確認視覺方向以前，不執行完整回歸、多尺寸截圖、效能分析或逐功能測試；不要在每次 CSS／動畫微調後重新跑測試。

### 先看方向、最後測試

本輪把「視覺與操作方向確認」和「正式測試」分成兩個階段。先完成全部 hubs 的可預覽候選版，讓使用者實際打開 `strava_cinema.html` 判斷是否符合期待；使用者明確回覆方向可以後，才進入完整測試與修正階段。

方向確認以前只允許最低成本的 smoke check：

- 修改後確認頁面能開啟一次，沒有阻斷畫面的致命錯誤。
- 新增路由時，只確認該入口能進入及能返回。
- 涉及 JavaScript 結構時，可以做一次快速語法檢查。

方向確認以前禁止：

- 逐一測試 9 個模組的完整功能。
- 反覆產生桌面與手機截圖。
- 完整 browser automation、Lighthouse、效能分析或長時間回歸。
- 為同一個小改動重跑所有路由、modal、圖表與互動。
- 撰寫冗長測試報告。

完成 Task 6 後，提供本機預覽網址與極短的改動摘要，然後停在「等待使用者確認方向」的閘門。除非使用者明確說「方向可以，開始測試」，否則不得進入 Task 7。
